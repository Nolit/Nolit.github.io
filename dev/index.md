# Dev logs

redoログがなぜ必要なのかを調べていた。ページファイルを書き込む時に問題が発生する確率とredoログを書き込むときに問題が発生する確率は同じではないか、というところから始まった。redoログの書き込みが成功してるのであれば復旧もできるだろうが、肝心のredoログもページファイル更新と同じようにディスクI/Oなのでリスクは同じではないのか。redoを成り立たせてるのはappendであること、fsyncすること、それからチェックサムを持つことだと整理した。例えばDBがページを8KBで管理しておりHDDが4KBでセクタを管理している場合、最低でも2回の書き込みが必要になる。この途中で落ちるとページの前半4KBが新しく後半4KBが古いといった不整合がおきる(torn page)。redoでもその確率は同じ(はず)だが、ファイルへのappendなので追記箇所より以前のデータが壊れない(はず)。redoログの各レコードはチェックサムを持ってるので検知可能だし、appendは書き込んだ順番が担保されるので壊れていないところまで適用するだけでよい。またredoファイルへの追記はOSのfsyncを呼び出しておりHDDに同期が取られる(HDDが嘘をつく可能性もあるがそこは信用するしかない)。なのでトランザクションcommit時にfsyncをすることでOSがキャッシュしたりせずに変更がHDDで確定する。データファイルにページを書くたびにfsyncをするとパフォーマンスが低下するので現実的ではない。まとめるとredoログ自体も壊れるじゃないかと疑問を持ったが、データファイルへの書き込みと同じように壊れる。ただし、1. チェックサムを持つので検知可能 2. appendなのでそれ以前のデータは無事 ということから影響範囲を限定し可能な限り復旧できる。またOSはwrite()を呼んでもブロックの変更をキャッシュし任意のタイミングでflushするので、トランザクションにおいてcommitをしても本当にその時点でHDDに書き込んだかは分からない。なのでfsyncする必要があるのだがデータファイルを変更するたびにするとパフォーマンスの低下を招くのでredoログにappendする時にfsyncしている（本当にそうなのかこれはまた後日考えたい）
